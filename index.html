반복적이고 위험한 작업을 자동화해 안전하고 효율적인 현장을 만드는 엔지니어. 아이디어보다 구현하고 검증하는 사람. 노바로보틱스 Co-founder·PM으로 딥테크 예비창업패키지 과제를 수행했고, 그 과정에서 전장·펌웨어·비전·백엔드·사업화를 한 번에 겪었습니다.

이 사이트는 이전 포트폴리오와 달리 결과 수치보다 어떤 문제를, 왜 그렇게 판단해서, 무엇을 바꿨고, 무엇을 배웠는지를 케이스 스터디로 적었습니다. 검증하지 못한 것은 검증하지 못했다고 적었습니다.

How I Work

기억에 의존하지 않고 기록을 쌓아 다음 문제를 풉니다

프로젝트마다 도메인은 달랐지만(로보틱스, 핀테크 계산, 마케팅 자동화, 영상 제작, 제조 데이터) 지켜온 기준은 같습니다.

01

구조화

"문제를 보면 먼저 구조부터 그린다"

Figma 와이어프레임 → 디렉토리 구조 → 구현 순서로 시작합니다. 바뀔 부분은 처음부터 어댑터로 분리하고, 조건 분기가 늘어날 로직은 상태 기반(FSM)으로 설계합니다. "명령 수락"과 "실제 완료"를 같은 것으로 착각하지 않는 비동기 설계는 펌웨어에서 웹까지 같은 습관으로 이어졌습니다.

02

검증 기준 먼저

"자동화한 결과는 검증 기준을 먼저 세운 뒤에 믿는다"

라벨링은 모델이 먼저 그리고 사람이 검수합니다. A/B 승자는 표본·SRM 기준을 통과할 때만 선언합니다. 정성적인 "설득력"도 R0~R7 규칙으로 쪼개 기계가 검수하게 만들었습니다. 규모를 키웠을 때 실제로 깨지는 지점을 데이터로 확인한 다음, 그 지점만 구조적으로 고칩니다.

03

기록과 번역

"증상 → 원인 → 확인 → 조치 → 리스크"

Notion 개발일지 98페이지, 블로그 회고 12편, GitHub DEVLOG로 남깁니다. 설계와 구현 상태를 README에 "구현 완료 / 다음 단계"로 구분하고, 같은 기술을 심사 성격(기술형·창업형·사회문제형)에 맞춰 다르게 설명합니다.

협업에서 바꾼 것 — 예창패 개발 중 팀원에게 "문제가 생기면 혼자 붙잡지 말고 먼저 공유해 달라"는 피드백을 받았습니다. 이후 막힌 문제는 원인, 시도한 방법, 필요한 도움을 먼저 공유하는 방식으로 바꿨고, 통합 검토에서 펌웨어 결함 4건을 함께 찾아낸 것도 그 결과였습니다.
