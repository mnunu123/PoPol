로보틱스 · AI 인터페이스

"로봇처럼 보이는 것"보다 "면접관처럼 느껴지는 것"에 집중했습니다

직접 휴머노이드를 설계하면 시간과 비용이 감당이 안 되고, 기성 로봇을 사면 표현력이 부족한 딜레마에서 InMoov 오픈소스(3D 프린팅, 서보 17개)를 골랐습니다.

Decision

전신 로봇이 아니라 "면접관처럼 느껴지는 인터페이스"로 목표를 다시 정의했습니다

전신 로봇을 다 구현하려 하면 개발 범위가 폭발적으로 늘어납니다. 그래서 눈(시선)·턱(발화 동기화)·목(끄덕임)·눈썹(감정 표현) 네 부위만 선별 구현하고, 팔 제스처나 보행은 범위에서 뺐습니다. 면접관 느낌을 내는 데는 움직임의 정밀도보다 타이밍과 시선, 발화 동기화가 훨씬 중요하다고 판단했기 때문입니다. 실시간 서보 제어 대신 상태별 Preset 모션(listen_pose, nod_small, thinking_pose)을 실행하는 방식도 같은 맥락입니다.

하드웨어는 얼굴 서보 15개(JX PDI 1109MG) + 목 2개(6221MG), Arduino Mega + PCA9685 16ch, 실리콘 피부 Ecoflex 00-10, 네오디뮴 자석 28개 구성입니다. 서보 전원과 보드 전원을 분리해 순간 전류 리셋을 막고, 조립 전 모든 서보를 90° 프리셋으로 맞추는 것이 필수였습니다.

Architecture

AI 서버와 로봇 컨트롤러를 Bridge API로 완전히 분리

AI 서버(STT → LLM → TTS → 평가)와 로봇 컨트롤러(서보 제어)를 Bridge API로 분리했습니다. 로봇 하드웨어가 준비되지 않은 단계에서도 AI 로직을 텍스트 기반으로 먼저 검증할 수 있어야 한다고 봤기 때문입니다. 1단계 텍스트 면접 흐름·LLM 연동 검증 → 2단계 음성 입출력 → 3단계 실물 로봇 연결 순으로, 리스크가 큰 하드웨어 조립을 가장 마지막에 두었습니다. 로봇 상태는 Idle → Asking → Listening → Evaluating으로 전이합니다.

MVP

OPIc 음성 모의면접 웹서비스 MVP (1인, 2026.03.18~27)

질문 생성 → 음성 답변 → STT → 답변 분석 → 피드백 → PDF 리포트까지 혼자 구현했습니다. FastAPI, Whisper STT, Claude API, ReportLab으로 세션 구조와 리포트 자동화를 설계했고, 로봇 연결 전에 AI 흐름을 먼저 검증한 단계입니다.

배운 점 — "로봇처럼 보이는 것"보다 "면접관처럼 느껴지는 것"에 집중하니 무엇을 만들고 무엇을 빼도 되는지가 훨씬 명확해졌습니다. 기술적으로 화려한 것과 목표에 필요한 것이 항상 같지 않습니다.
