빗물받이 막힘은 민원이 들어오기 전에 먼저 알아야 했습니다

도시 빗물받이가 막히면 우기 침수로 직결되는데, 현재는 사람이 순회 점검하는 방식이라 사각지대가 많고 예방적 관리가 안 됩니다. 현장 청소·데이터 수집 로봇, 관제 웹 플랫폼(Drain Sight), 위험도 예측 AI를 결합해 "사진 한 장이 지금 청소가 필요한가라는 판단으로 이어지는" 구조를 만들었습니다.

System

현장 로봇부터 클라우드 관제까지 한 흐름으로 설계했습니다

Jetson Orin이 ZED Mini 카메라 3대로 인식하고, STM32F407이 스테퍼 4축·윈치(24V 릴레이 2개)·실린더·서보 걸쇠를 구동합니다. 앱에서 올린 현장 사진과 GPS는 클라우드 DB에 "분석 대기" 상태로 먼저 적재되고, 로컬 GPU 서버가 위험도·청소 동선·강수 결합 침수 히트맵을 계산한 뒤 결과를 다시 DB에 기록해 관제 웹에서 봅니다.

왜 이렇게 나눴는가 — ML·알고리즘 연산은 비용이 크고 GPU가 필요하기 때문에, 상태만 가볍게 저장하는 클라우드 DB와 무거운 연산을 전담하는 로컬 서버를 분리해야 비용과 성능을 동시에 잡을 수 있다고 봤습니다. 그리고 "정확한 수치를 뽑는 것"과 "그 수치를 사람이 이해하게 설명하는 것"은 다른 문제라서, 수치 연산(ML+알고리즘)과 자연어 리포트 생성(LLM)을 처음부터 다른 단계로 분리했습니다.

Problem 1 · Data

360시간짜리 수작업 라벨링을 "모델이 먼저 그리고 사람이 검수"하는 구조로 바꿨습니다

빗물받이 사진 1장에 구멍이 60개 이상 있습니다. 팀원 4명이 나눠도 장당 약 6분, 3천 장 기준 360시간 이상이 나왔고 예창패 3~4개월 안에는 불가능했습니다. 공개 데이터셋에는 구멍 단위 Instance Segmentation 데이터가 없었습니다.

그래서 라벨을 "그리는" 작업을 "확인하는" 작업으로 바꿨습니다. 원본 364장만 수동으로 라벨링하고 증강으로 914장(Train 825 / Valid 59 / Test 30)을 만들어 1차 모델을 학습시킨 뒤, 그 모델과 Mobile-SAM이 나머지 이미지의 구멍 마스크를 먼저 생성하고 사람은 오검출만 고쳤습니다. 검수본으로 재학습을 반복하면서 성능이 점진적으로 올라가는 걸 확인했습니다.

Problem 2 · Firmware

main.c 하나에 몰린 로직을 이벤트 기반 FSM + 5계층으로 재설계했습니다

초기에는 STM32 펌웨어의 모든 로직이 main.c 하나에 있었습니다. 기능이 하나 늘 때마다 조건 분기가 기하급수적으로 늘었고 HOME·MOVE·WINCH 동작이 충돌했습니다. 릴레이 두 개가 동시에 켜지면 하드웨어가 파손될 수 있는 구조였습니다.

원인을 "상태 관리 방식 자체"로 정의하고 이벤트 기반 FSM으로 재설계했습니다. 각 상태에서 허용되는 명령을 명시적으로 정해서(HOME 진행 중에는 WINCH 명령을 NACK) 충돌 가능성을 상태 전이 규칙 자체에서 차단했습니다. 계층은 main → app(명령 파싱·FSM) → services → drivers → bsp(핀맵 안전 규약) 5단으로 나눴습니다. 이후 ACT:CYLINDER, ACT:MOVE 같은 신규 명령을 추가할 때 app_cmd.c만 수정하고 services·drivers는 손대지 않았습니다.

프로토콜은 ACK/NACK(명령 수락 여부)와 DONE/FAIL(실제 완료)을 분리한 비동기 구조입니다. 윈치 방향 전환은 OFF → 데드타임 50ms → ON 순서를 강제했고, 호밍은 SEEK → ABSORB → RESET → BACKOFF → SET_ZERO 5단계 FSM입니다. host_test 디렉토리를 두어 보드 없이 PC에서 FSM과 파싱을 테스트했습니다.

BEFORE
  • 모든 제어 로직이 main.c 한 파일
  • 기능 추가마다 조건 분기 폭증
  • HOME · MOVE · WINCH 충돌 반복
  • 릴레이 동시 ON 가능 → 파손 위험
AFTER
  • 5계층 분리, 상태 전이 규칙으로 충돌 차단
  • 신규 명령은 app_cmd.c만 수정
  • ACK/NACK와 DONE/FAIL 분리
  • 데드타임 50ms, 부팅 시 모터·윈치 비활성
통합 검토에서 찾은 결함 4건 — 16개 파일을 통합 검토하면서 DIR 규약 뒤집힘, TIM3 스텝 펄스와 서보 PWM 충돌, Y2 미장착 처리 누락, 핀맵 불일치(PB0 vs PC6)를 실기판 테스트 전에 잡았습니다.
Problem 3 · Reliability

릴레이 노이즈 오동작 100% → 0% — 원인을 하드웨어와 소프트웨어 양쪽에서 끊었습니다

OPEN 동작 중 바닥 버튼이 눌리면 CLOSE 버튼으로 오인식되어 CLOSE가 즉시 실행되는 문제가 매번 발생했습니다. 추측으로 고치지 않고 역기전력(전류가 끊기는 순간 생기는 반대 방향 전압) → 배선 → 소프트웨어 순으로 원인을 좁혔습니다. 릴레이 스위칭 시 전압 서지, 버튼 신호선이 전원선과 근접 배치된 것, 긴 배선으로 인덕턴스가 커진 것이 겹쳐 있었습니다.

하드웨어 대책 4가지(페라이트 코어, VCC/GND 트위스트 1cm당 1~2회, 릴레이 전원단 0.1µF 바이패스 + STM32 전원 100µF 전해 + 0.1µF, 버튼선과 릴레이선 분리 배선)를 모두 적용하고, 소프트웨어로 디바운싱 20ms 후 재확인과 OPEN 상태에서 CLOSE 입력 800ms 마스킹을 더했습니다. 2026.01.14 기준 100회 반복 테스트에서 오동작 0건이었습니다.

배운 점 — 고장 탐구는 재현 조건(100회)을 먼저 정해야 끝낼 수 있다는 것을 체감했습니다. 이후 모든 수정은 "몇 회 테스트에서 몇 건"으로 기록합니다. 향후 과제로 PCB화, 실드 케이블, 옵토커플러 절연을 남겨 두었습니다.
Problem 4 · Power & Electrical

윈치 돌입전류로 MCU가 리셋되던 문제, 그리고 직접 손으로 만든 전장

디버거에 "Target is not responding"이 뜨며 윈치 시동 순간 STM32가 리셋됐습니다. 원인은 윈치 돌입전류가 평소의 5~10배(0.1~0.2초)로 흐르면서 전압이 2.7V 이하로 떨어지는 브라운아웃이었습니다. MCU/모터 전원 분리, 대용량 커패시터, PWM 소프트스타트, MOSFET 스위칭을 대책으로 설계했습니다.

전장은 COM=24V, STM32 GPIO는 릴레이 IN핀에만 연결, 강전/약전 완전 분리를 원칙으로 잡았고, DIN 레일·케이블 덕트·항공커넥터 GX16으로 존(전원/제어/드라이버)을 나누는 구조를 조사해 적용했습니다. 선형 스테퍼모터는 볼트가 빠져 전부 분해했다가 내부 구슬 20여 개가 끼여 철사와 망치로 복구했고, 가정용 청소기를 해체해 전원부를 재배선하고 2핀 스위치 제어로 개조했습니다.

Problem 5 · Measurement

사진 한 장으로는 알 수 없는 퇴적물 부피를 깊이 카메라로 정량화했습니다

퇴적물이 "얼마나" 쌓였는지를 숫자로 알아야 청소 우선순위를 매길 수 있는데, 일반 사진으로는 3차원 정보인 부피를 알 수 없습니다. ZED Mini 스테레오 카메라를 빗물받이 위에서 아래를 향하게(top-down) 설치했습니다. 청소 후 기준 깊이(10프레임 시간 평균)와 청소 전 깊이의 차이로 높이맵을 만들고, YOLOv8 쓰레기 세그먼테이션 마스크만 남기고, 그레이팅(철망)은 별도 모델로 검출해 제외하거나 인페인팅하고, 신뢰도 90 이하 픽셀을 걸러낸 뒤, 픽셀별 실제 면적 × 높이를 합산합니다. 설계 단계에서는 RANSAC 바닥 평면 추정도 검토했습니다.

가장 중요했던 판단은 "완벽한 정확도"를 포기한 것입니다. 물이 고여 있으면 거울처럼 반사해 스테레오 매칭이 불안정해지고 실제 현장은 실험실처럼 깨끗하지 않습니다. 그래서 목표를 평균 오차 5~10%(최악 15~20%), 1~5 FPS로 처음부터 낮춰 잡고, 현장 제약(물·가림·노이즈)을 설계 조건에 넣었습니다.

02

03

신뢰도 90 이하 제외, 3중 필터링
05

검증 범위 — 110cm 거리 테스트 코드와 저장소(threebot_weight) 구현까지 완료했습니다. 실측 부피 대비 정확도 검증은 아직 하지 못했습니다.
Problem 6 · Scale

400만 건에서 멈추던 지도를 공간 인덱스 + 뷰포트 렌더링으로 풀었습니다

검증용으로 대구 지역에 빗물받이 더미 데이터를 생성해 지도에 뿌리는 스크립트를 짜서 테스트하다가, 규모를 400만 건까지 늘리자 지도를 조금만 움직여도 렉이 걸려 쓸 수 없는 수준이 됐습니다. 원인을 "매번 전체 데이터를 순회 조회하는 구조"로 정의하고, DB에 공간 인덱스(spatial index) 마이그레이션을 적용했습니다. API는 GET /drainage/markers?minLat…maxLng BBOX 조회로 바꿔 지도 idle 이벤트 때마다 뷰포트만 요청하고, 프론트는 deck.gl 뷰포트 렌더링으로 전체 포인트 일괄 그리기를 없앴습니다.

네이버 지도로 전환할 때는 문제 5개(moveend 미지원 → idle, 캔버스 pointer-events, getBounds, overlay.draw 무한 재귀, getSW/getNE)를 차례로 풀고 naver.maps.OverlayView를 상속한 DrainageOverlay로 재작성해 코드 200줄 이상을 줄였습니다. 배포된 임시 LIMIT 200 때문에 1,000건 중 200건만 보이던 버그도 추적해 제거했습니다.

BEFORE
  • 전체 데이터 순회 조회
  • 드래그마다 렉, 사실상 사용 불가
  • 전체 포인트 일괄 렌더
AFTER
  • 공간 인덱스 + BBOX 뷰포트 조회
  • 규모와 무관하게 부드러운 이동
  • deck.gl 뷰포트 렌더링
배운 점 — 일단 작게 동작하는 걸 만들고, 규모를 키웠을 때 실제로 깨지는 지점을 데이터로 확인한 다음 그 지점만 구조적으로 고친다. 처음부터 완벽한 구조를 설계하려다 시간을 쓰기보다 병목이 어디서 생기는지 눈으로 확인하고 고치는 쪽이 더 빠르고 정확했습니다.
Constraint · Public Sector

공공기관 보안 요건을 3중 차단 구조로 풀고, 편의보다 제약을 우선했습니다

지자체·공공기관 대상 서비스라 해외 클라우드를 쓰면 GS 인증 등으로 사업 참여 자체가 막힐 수 있고, DB가 외부에 직접 노출되면 안 된다는 정책 제약이 있었습니다. 국내 클라우드(NCP) + ACG 방화벽, PostgreSQL 15 Docker 컨테이너를 127.0.0.1:5432에만 바인딩, FastAPI 서버 경유 접근만 허용하는 3중 구조로 풀었습니다. 전용 계정 threebot_app에는 필요한 테이블의 CRUD만 부여하고 DROP·TRUNCATE는 계정 단위에서 차단했습니다.

asyncpg를 고른 이유는 sync SQLAlchemy는 await해도 블로킹되기 때문이고, MySQL에서 PostgreSQL로 \copy로 이관했습니다. "운영 중에는 DB에 직접 접근하기 불편한 게 오히려 안전하다"는 기준을 세우고 편의성보다 제약 조건을 우선했습니다.

기술을 만든 뒤 시장 반응까지 직접 확인했습니다

예비창업패키지 과제(정부지원금 6,100만 원, 5,316만 원 집행, 87.14%)에서 기술 개발 외에 공공기관 제출 서류·사업계획서·진행보고서, 지출 정리·예산안·정산, 부품·외주 발주·견적 비교·납기 관리, 팀 일정·회의·대외기관 연락, IR 피칭 자료 제작과 발표를 전담했습니다. Claude Code로 회의록·구매·제출서류 초안을 자동화했는데 첫 적용에서 오류가 약 8건 나와 검수 기준으로 누적했습니다.

팀 성과로는 서울시 물재생계획과 협력으로 빗물받이 cm 단위 정밀 GPS 데이터 활용 권한을 확보하고, 강남구청 실무 미팅으로 파일럿 적용을 타진했으며, 프레스토솔루션 모터 현물 후원과 수산건설(김포 준설업체) 공동 R&D 논의를 진행했습니다. 목표 달성도는 흡입 모듈 100%(18cm 흡입구, 3중 흡입 모터, 물 제외 쓰레기만 흡입), VLA 개폐 그리퍼 80%(삽입 오차 ±5mm), 관제 플랫폼 60%로 전체 70%였고, 신규 고용 3명, 최종 우수기업 선정으로 청년창업사관학교 서류 면제를 받았습니다.

2025년 9월부터 12월까지 같은 프로젝트로 9개 대회에서 수상했는데, 기술형 대회는 구현 가능성과 검증 데이터로, 창업형은 사업 모델과 시장으로, 사회문제형은 공공 활용성과 침수 예방 효과로 같은 기술을 다르게 풀어 설명했습니다. 발표는 직접 수행했습니다.
