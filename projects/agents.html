AI 자동화 · 멀티에이전트

AI 도구를 써본 것이 아니라, 반복 작업을 자동화 구조로 바꿨습니다

공통 원칙은 세 가지입니다. 에이전트 하나가 모든 판단을 하지 않도록 파이프라인으로 쪼갠다, 중간 산출물을 JSON으로 남겨 단계별로 재실행한다, 선택 이유를 데이터에 함께 기록한다. 모든 수치는 GitHub 저장소와 DEVLOG 기준이며 실사용 트래픽 지표는 없습니다.

Pipeline 1

5개 에이전트가 협업해 상세페이지를 만듭니다

쇼핑몰 상세페이지 제작이 기획 → 카피 → 디자인 → 이미지 순서로 매번 비슷한 사고 흐름을 반복하는 노동집약적 작업이라는 데서 출발했습니다. 단일 프롬프트로 "전체를 만들어줘"라고 하면 결과 일관성과 길이가 제멋대로였기 때문에, 정보수집(Haiku) → 리서치(Sonnet) → 카피 13섹션(Sonnet) → 디자인 방향(Haiku) → 이미지 프롬프트(Sonnet) → Gemini 이미지 생성으로 역할을 분리했습니다. 난이도가 낮은 단계는 저비용 모델, 품질이 중요한 단계는 고성능 모델을 써서 비용도 최적화됩니다.

초기에는 에이전트 간 데이터를 메모리로만 넘겼는데 파이프라인이 중간에 실패하면 처음부터 다시 돌려야 해서, 각 에이전트가 JSON으로 중간 산출물을 저장하도록 바꿔 특정 단계만 재실행할 수 있게 했습니다. 04 에이전트의 스타일 프리셋을 모든 이미지 프롬프트에 주입해 섹션 간 화풍 불일치도 해결했습니다. 입력 후 3~5분 안에 1200×7000px PNG/PDF가 나옵니다.

Pipeline 2

"그림 속 버튼은 클릭이 안 된다" — 신뢰할 조건에서만 A/B 승자를 선언합니다

설계할 때는 생각 못 했는데, 실제 캠페인에 써보려는 단계에서 AI가 이미지 안에 그려 준 "지금 신청하기" 버튼이 그림일 뿐 클릭이 안 된다는 걸 뒤늦게 깨달았습니다. 이미지를 다시 그리게 하면 디자인 품질이 흔들릴 위험이 있어, 이미지는 그대로 두고 % 좌표 기반 CTA 버튼을 얹고 반투명 마스크(blur 10px)로 가짜 버튼 잔상을 가렸습니다. "생성은 AI에게, 인터랙션은 별도 레이어에서"로 역할을 나눈 것입니다.

GA4로 lp_impression → lp_cta_click → lp_reserve_submit 3단계 이벤트를 추적하고, A/B 배정은 URL → localStorage → 쿠키 → 랜덤 50:50(30일 유지) 순으로 결정합니다. ab_decide.py는 전체 제출 ≥ 10, variant당 노출 ≥ 100, SRM 불균형 ≤ 20%, CVR 차이 ≥ 0.2%p를 모두 통과해야만 승자를 선언합니다.

실제 결과 — 실제 배포에서 노출은 4건, 클릭 2건이었습니다. 승자 선언이 아니라 collect_more가 나왔고, 이 프로젝트에서 검증한 건 승자가 아니라 "추적·집계·판정 파이프라인이 실 배포 환경에서 끊기지 않고 도는가"였습니다. 자동화를 만들 때 "신뢰할 만한 조건에서만 결론을 내리게 막아두는 것"도 자동화 설계의 일부라는 걸 배웠습니다. 설계된 도구 11개 중 4개(scraper, gemini_analyzer, ga4_client, ab_tester)가 구현됐고 README에 구분해 두었습니다.
Pipeline 3

정성적인 "설득력"을 R0~R7 규칙으로 쪼개 기계가 검수하게 했습니다

build_deck.js 명령 1개로 PPTX + HTML 슬라이드 + 스토리보드 + 검증 리포트 + 카피 리포트 5종이 나옵니다. R1 제목=결론(주제형 제목이면 실패 처리 + 수정안 제시), R2 소유권 테스트(범용 표현 감지 시 실패), R6 줄글 금지(30자 이상 문장 분할 제안) 같은 규칙을 명문화해 기계적으로 검증합니다. 목표 문구에 "안내/지원/정책" vs "설득/투자/제안" 키워드가 있는지에 따라 가이드형/설득형/브리핑형 구성을 자동 선택합니다. research → organizer → critic → design → pptx Sub-Agent 버전도 병행했고, 12장 슬라이드를 끝까지 생성해 실제 IR 발표 자료에 썼습니다.

Pipeline 4

쇼츠 레퍼런스 자동 수집 — 선택 이유를 데이터에 함께 기록

한국어 키워드 → 번역 → 도우인 검색 → 1분 미만 필터 → 가중 랭킹 → yt-dlp 다운로드까지 명령 1회, 30~60초입니다. 가장 큰 벽은 봇 차단이었는데 원인이 브라우저 시그니처라는 걸 확인하고 실제 설치된 Chrome(channel="chrome")을 쓰자 차단률이 크게 낮아졌습니다. 조회수만 보면 광고성 영상이 상위에 오르기 때문에 좋아요 ×3.0, 댓글 ×5.0, 공유 ×2.0, 조회 ×1.0으로 사용자 반응에 가중치를 뒀고, selected_reason을 JSON으로 남겨 왜 이 영상이 뽑혔는지 추적할 수 있게 했습니다. 2~4단계(자막·편집·업로드)는 미구현으로 README에 명시했습니다.

Pipeline 5

코드로 만드는 영상 — Remotion

인라인 AI 소개 영상(3분, 13씬)과 Remotion 자체를 소개하는 영상(1분, 9씬)을 1920×1080 30fps로 만들었습니다. 씬 타이밍을 constants.ts의 TIMING 객체에 프레임 단위로 단일 정의하고, ElevenLabs TTS 파일명을 씬 ID와 1:1 대응시켜 자막 수정 시 오디오가 안 맞는 문제를 파일명 규약으로 예방했습니다. 키네틱 아트 제작 서비스 랜딩(v1 → v2)과 함께 영상 + 웹 복합 결과물로 완성했습니다.

Pipeline 6

포트폴리오 메이커 — 302 리다이렉트를 실패로 오인하던 문의 폼

취준생이 포트폴리오를 못 만드는 이유가 "콘텐츠가 없어서"가 아니라 "정리가 안 돼서"라는 관찰에서 토스/당근/빗썸/네이버/카카오 무드로 대신 정리해 주는 서비스 랜딩을 만들었습니다. 무드 5종의 이름·소개·타겟·컬러를 lib/template-data.ts 단일 소스로 관리하고, 프로젝트 전용 Claude Code 스킬 3개(pastel-brand-system, template-gallery-builder, ui-polish-review)로 디자인 드리프트를 막았습니다.

문의 폼을 Google Apps Script로 연동하는데 요청이 분명 성공했는데도 클라이언트에서는 계속 실패로 처리됐습니다. 처음엔 내 코드를 의심해 요청 로직을 계속 고쳤는데, 원인은 Apps Script 웹앱이 실행 후 302로 리다이렉트하고 fetch의 res.ok가 이걸 실패로 보는 것이었습니다. 상태 코드 대신 요청이 오류 없이 나갔는지로 판단하도록 바꾸고, URL이 브라우저에 노출되는 게 마음에 걸려 서버 API 라우트 뒤로 옮겼습니다. 에러를 만나면 내 코드부터 의심하는 습관은 맞지만, "이 외부 서비스가 애초에 뭘 보장하는지"까지 확인하는 습관을 다시 붙였습니다.
